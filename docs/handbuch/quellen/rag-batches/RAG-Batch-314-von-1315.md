Im Bereich Reporting wurden mehrere Verbesserungen an den Data Products (DP) umgesetzt, die die Bereitstellung und Verarbeitung von Finanz- und Basisdaten betreffen.

Für die Financials-Data-Products wurde die monatliche Datei- bzw. Delta-Verarbeitung optimiert. In oneSCM werden die Daten (DCS) automatisch über eine API importiert, sobald eine Datei hochgeladen wird; der Upload löst den Import aus. In den Legacy-Systemen startet automatisch ein ETL-Ablauf, sobald eine Datendatei zusammen mit der zugehörigen EOF-Markierungsdatei (End-of-File) im CFT-Verzeichnis des Nemesis-Raw-Buckets abgelegt wird.

Neu geregelt ist der Umgang mit Dateien, die nicht in der richtigen Reihenfolge eintreffen. Fehlt beispielsweise die Datei für August, während die Datei für September vorliegt, prüft das System die Reihenfolge der Dateien. Fehlt die Datei eines Monats und trifft eine Datei für einen späteren Monat ein, verarbeitet das System die späteren Dateien weiter. So wird verhindert, dass die Verarbeitung stoppt, wenn Nemesis für einen Zeitraum keine Datei liefern kann. Es muss jedoch prozessual sichergestellt werden, dass Nemesis die Dateien in der richtigen Reihenfolge sendet. Ist das nicht der Fall, müssen die Dateien manuell über einen Initial Load erneut hochgeladen werden. Dabei ist darauf zu achten, dass dieser manuelle Lauf sich nicht mit dem aktuell geplanten Lauf überschneidet. Im Legacy-Ablauf verfolgt die Lambda-Funktion dazu die Reihenfolge aller hochgeladenen Dateien. Der AWS-Glue-Job prüft die Reihenfolge und überspringt bei einer Lücke den betroffenen Monat, um die Dateien der späteren Monate zu verarbeiten. Sobald die fehlende Datei von Nemesis geliefert wird, muss sie manuell hochgeladen werden, zusammen mit den Dateien der Folgemonate desselben Jahres in der richtigen Reihenfolge. Diese Folgedateien können aus dem Backup-Ordner heruntergeladen werden.

Zusätzlich wird bei fehlenden Monatsdateien eine Warnung erzeugt. Im Legacy-Ablauf löst der Glue-Job beim Erkennen einer Lücke eine E-Mail-Benachrichtigung aus. Auch hier muss sichergestellt werden, dass die fehlende Datei im nächsten Lauf manuell nach CFT hochgeladen wird, ebenso alle nachfolgenden Dateien der betroffenen Reihenfolge.

Außerdem wurde der Umgang mit Datensätzen ungültiger Länge verbessert. Früher unterbrach ein solcher Datensatz den gesamten Verarbeitungsablauf. Jetzt protokolliert das System den Fehler, überspringt den betroffenen Datensatz und verarbeitet die übrigen Datensätze der Datei weiter. Auch die anderen Dateien im Prozess werden weiterverarbeitet. Über die übersprungenen Datensätze wird eine separate Fehlerdatei erstellt. Sie enthält den Namen der Datei, in der der Fehler aufgetreten ist (zum Beispiel xyz-nov.txt oder xyz-aug.txt), die Datensatznummer oder Kennung, sofern verfügbar, bzw. die Vertragsnummer und gegebenenfalls Berichtsjahr und -monat (period_year und period_month aus dem C-Satz) sowie den Zeitstempel des Fehlers. Für Fehlerfälle ist eine geeignete Benachrichtigung vorgesehen.

Der Zeitplan der Base-DP-Jobs wurde angepasst: Sie laufen nun am 4. statt am 3. eines jeden Monats. Zudem wurden fehlende UK-Datenaktualisierungen für 09/2025 in den Base Data Products im Reporting nachgezogen.

Alle Data Products werden künftig im Iceberg-Format bereitgestellt, damit Daten inkrementell (als Delta) geliefert werden können. Betroffen sind SC Base Contracts, SC Base Revenue, SC Base Cost bzw. SC Base Van Cost, SC Base Customer, SC Financials und ISP. Jedes Data Product steht in zwei Formaten zur Verfügung: als Vollladung (Plain Parquet) und als Delta (Iceberg). Voraussetzung ist, dass alle Tabellen Datensätze mit eindeutiger Kennung verarbeiten. Bei Schadensdaten aus Asset-Claims werden die Daten für die Kostentabelle nach country_code, sc_number_pk, invoice_number_pk und damage_code gruppiert; für Schadenspositionen ist keine Gruppierung nötig.

Zur Umsetzung gehören Partitionsschlüssel auf Basis der Iceberg-Änderungen sowie eine geeignete Housekeeping-Richtlinie (maximal etwa 10 Snapshots), damit nicht zu viele Snapshots gespeichert werden. Für den Markt DE wird ein Snapshot-Vergleich in den Base Data Products eingeführt. Bisher lief das Data Product in einer Schleife je Markt und schrieb jedes Mal nach Iceberg, wodurch pro Lauf 16 Snapshots entstanden, bei gelöschten Daten weitere 16, und Änderungen nur durch aufwendigen Quelle-Ziel-Vergleich erkennbar waren. Künftig wird ein einziger konsolidierter Snapshot geführt: Die Daten aller Märkte werden in einem gemeinsamen Data Frame gelesen und anschließend einheitlich im Ziel aktualisiert oder gelöscht. Dadurch lassen sich Snapshots den einzelnen Märkten zuordnen und Vergleiche marktübergreifend durchführen.

Die Daten sind aktuell, vollständig und konsistent im definierten Attributformat und stehen sowohl aus den Legacy-Anwendungen als auch aus oneSCM zur Verfügung. Die Dokumentation von Data Product, UDM und Mapping entspricht der aktuellen Umsetzung. Nach Abschluss aller Änderungen werden alle Märkte und Data Products durchgängig (Ende-zu-Ende) getestet.
