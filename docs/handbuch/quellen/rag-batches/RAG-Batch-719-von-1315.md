**Versand von Provisionsrechnungen an NEMESIS**

Als Administrator können Sie die Provisionsrechnungen von Händlern an NEMESIS übermitteln. Sie werden dabei im Ereignis „DealerInvoice“ gesendet. Dabei werden die Attribute nach festen Mapping-Regeln aus oneSCM befüllt. Die ZGUID ist eine generierte ID mit 32 Zeichen. Länderkennzeichen, Fahrgestellnummer, Vertragsnummer sowie die Händler-ID (Partnernummer bzw. Vega-ID) stammen direkt aus oneSCM. Die Händlerart richtet sich nach dem Rechnungstyp, also danach, ob der Händler zum Konzern gehört: „0“ (DCInternal) steht für interne, „1“ (DCExternal) für externe Händlerprovisionsrechnungen. Als Händlerrechnungsnummer wird die oneSCM-Rechnungsnummer verwendet, als Erstellungsdatum das Datum der Provisionsrechnung. Der Reparaturkilometerstand entspricht dem letzten bekannten Kilometerstand, falls zum Zeitpunkt der Provisionsabrechnung keine aktuelleren Informationen vorliegen. Als Reparaturdatum wird das Rechnungserstellungsdatum übernommen. Das Feld „ExternalInvoice“ wird immer mit „X“ gekennzeichnet, da es sich um keinen VEGA-Anspruch handelt. Außerdem werden die Währung und der Netto-Gesamtbetrag übermittelt, ebenso die VIN bzw. die FIN als Fahrgestellnummer. Der Rechnungstyp lautet „SCOM“. Das Feld „Own Retails“ enthält „X“, wenn es sich um Own Retails handelt, andernfalls bleibt es leer. Die Felder „ContingentUsed“ und „AmountTotalInsuranceFee“ bleiben ohne Wert (NULL), „Reinsured Type“ und „Reinsured Percentage“ bleiben leer. Die FI-Dokumentnummer enthält bei externen Händlern die FI-System-Rechnungsnummer und bleibt bei internen Händlern leer.

Das Ereignis wird bei internen Händlerprovisionen im Status „Export“ und bei externen Händlerprovisionen im Status „FI-Document“ an NEMESIS gesendet.

**Verarbeitung von i156-Dateien in der richtigen Reihenfolge und erneute Verarbeitung korrigierter Dateien**

oneSCM importiert i156-Dateien in der Reihenfolge, in der sie von VEGA erzeugt wurden. Liegen im S3-Bucket aus dem CFT-Ablauf mehrere Dateien gleichzeitig vor, werden sie anhand des Zeitstempels verarbeitet. Dieser steht im Satztyp 01 an den Positionen 049 bis 074. Beim Import wird zudem geprüft, ob der Zeitstempel der Datei neuer ist als der der zuletzt importierten Datei. Ist er neuer, wird die Datei verarbeitet. Ist er älter, wird die Datei übersprungen und ein Fehler in Datadog protokolliert.

Werden einzelne Ansprüche wegen fehlerhafter Daten übersprungen, wird der Fehler in Datadog protokolliert. Der Administrator erhält darüber eine gesammelte Benachrichtigung mit dem Text „Please review the skipped claims in DataDog“.

Damit korrigierte Ansprüche nachträglich importiert werden können, kann eine Datei mit demselben Zeitstempel erneut verarbeitet werden. Dafür gibt es im Admin-Bereich auf der Seite „Cross File Transfer“ einen zusätzlichen Reiter zum Hoch- und Herunterladen von Dateien nach bzw. von S3. Er wird direkt nach dem Reiter „Cross File Transfer“ angezeigt. Die Suche trägt den Titel „Search Files“ und bietet die Kriterien Dateiname (maximal 50 Zeichen), Datum, Schnittstellen (Mehrfachauswahl, derzeit nur i156) und „Uploaded by“ (maximal 10 Zeichen). Weitere Filter gibt es nicht. Die Ergebnistabelle zeigt Dateiname, Schnittstelle, Upload-Datum, Benutzername des Hochladenden und eine Aktion zum Herunterladen der Datei. Sie ist standardmäßig nach „Uploaded on“ absteigend sortiert, sodass die zuletzt hochgeladene Datei oben steht. Im Dialog „Upload File“ heißt das Eingabefeld „Interface“ und bietet nur eine Schnittstelle an. Unterstützt werden die Dateitypen .dat und .txt. Sobald eine Datei hochgeladen wurde, startet ihre Verarbeitung.

Wird eine Datei mit demselben Zeitstempel erneut verarbeitet, vergleicht oneSCM die Ansprüche mit den Daten in der Datenbank. Stimmen Zeitstempel und Entscheidungsnummer überein, wird der Anspruch übersprungen. Importiert werden nur neue Ansprüche, die noch nicht in der Datenbank vorhanden sind. Ein typisches Beispiel: Einzelne Ansprüche einer Datei sind fehlerhaft, etwa wegen einer falschen Fahrgestellnummer oder eines falschen Produkttyps. Der Second-Level-Support analysiert das Problem und erstellt manuell eine Datei mit demselben Header wie die fehlerhafte Datei, die den korrigierten Anspruch enthält. Diese Datei wird anschließend hochgeladen.

**Klassifizierung von Werkstattrechnungen in der Detailansicht**

Die Antwort des Endpunkts zu den Details einer Werkstattrechnung enthält nun zusätzlich das Feld „workshopInvoiceClassificationType“ mit der Klassifizierung der Werkstattrechnung. Damit kann die Oberfläche erkennen, welche Rechnungen aus i156 importiert wurden, und entsprechend die Umsatzsteuerwerte und weitere Summen auf den Ansichtsseiten der Werkstattrechnungen ein- oder ausblenden.
